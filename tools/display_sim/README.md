# MP2040 display simulator

Renders the **real** on-device display code (mini menu, button layout, remap,
splash, screen savers) on your computer, without flashing a board. It compiles
the actual firmware sources in `src/display` against a small host shim and shows
the resulting 1bpp framebuffer in an SDL2 window and/or writes PNGs, so what you
see is pixel-for-pixel what the panel gets.

## Build

```sh
tools/display_sim/build.sh              # default board: Fightboard (128x64, has a display)
tools/display_sim/build.sh -b Springboard
tools/display_sim/build.sh -c           # clean
```

The binary lands at `tools/display_sim/build/mp2040-display-sim`. Rebuild with a
different `-b <board>` to preview another board's layout/display settings. The
board is baked in at build time from `configs/<board>/BoardConfig.h` (the same
defines the firmware uses), so the display size, orientation, splash and
`BOARD_DISPLAY_LAYOUT` all match that board. `build.sh` also records the baked
board in `build/board` so the screenshot scripts pick the matching
`configs/<Board>/board.svg`.

This is a host tool only: it is not part of the firmware CMake build and cannot
end up in a UF2.

## Interactive

```sh
tools/display_sim/build/mp2040-display-sim
tools/display_sim/build/mp2040-display-sim --screen buttons
```

| key | action |
| --- | --- |
| arrows | menu navigation |
| Enter / Space | select (B1) |
| Esc / Backspace | back (B2) |
| `1`..`5` | splash / buttons / menu / remap / saver |
| Tab | cycle screens |
| `[` `]` (or `-` `=`) | scale down / up |
| `f` | toggle 180° flip |
| `i` | toggle invert |
| `s` | save a PNG to `--shot-dir` (default `screenshots/`) |
| `q` | quit |

## Headless / screenshots

```sh
# one frame to a PNG (no window/display needed)
tools/display_sim/build/mp2040-display-sim \
  --screen menu --nav down,down,down,down,select --scale 4 --png out.png

# a standard set of bare framebuffer states
node tools/display-screenshots.mjs --scale 4

# composite onto the board's SVG (inside the `oled` element)
node tools/board-oled-screenshots.mjs --scale 3

# ...and additionally as pixel-accurate SVGs (board-oled-<state>.svg)
node tools/board-oled-screenshots.mjs --svg --scale 3
```

By default the composite is sized so the OLED is **1:1** (each display pixel =
one output pixel); `--display-scale N` picks that ratio explicitly and
`--scale N` overrides with a whole-board multiplier instead (e.g. `--scale 3`
for a 3x board, OLED at ~2px/pixel).

`--nav` replays menu/remap actions (`up,down,left,right,select,back`).
`--time-ms` fixes the virtual clock so animated screens (splash close-in, savers)
capture deterministically. `--fg`/`--bg` tint the output (e.g. `--fg 7fd0ff` for
a blue OLED look). `--size 128x32` forces a 128x32 panel. `--config` renders
web config mode, where the footer shows `CFG at 192.168.7.1` instead of input
history.

`display-screenshots.mjs` writes bare framebuffer PNGs (`display-<state>.png`);
`board-oled-screenshots.mjs` overlays each frame inside the `oled` element of
`configs/<Board>/board.svg` (found from `build/board`, or `--board` to
override) and captures the board in headless Chromium. The 128x64 frame is fit
with `xMidYMid meet`, so it letterboxes inside the panel rect and covers the
on-SVG logo — like the board with its screen lit (`board-oled-<state>.png`).

Pass `--svg` to also serialize each composite as a **pixel-accurate SVG**
(`board-oled-<state>.svg`): the simulator writes a 128x64 1bpp mask
(`--mask`), the page turns every lit pixel into a 1x1 `<rect>` over the panel
(`shape-rendering="crispEdges"`, letterboxed like the PNG), and the board +
pixels are saved as a standalone, Inkscape-openable SVG that stays crisp at
any zoom. Output is both `.png` and `.svg` per state.

Run `... --help` for the full option list.

## How it works

- `main.cpp` initialises `GPGFX` exactly like `DisplayController`, instantiates
  the real screen classes and feeds them navigation actions, then reads the
  framebuffer back with the public `GPGFX::getPixel()` and blits it to SDL2 or a
  PNG.
- `shim/` shadows `storagemanager.h`, `drivermanager.h`, `system.h`, `version.h`
  and the pico/tinyusb headers the display layer touches, providing in-memory
  implementations (plus the pico i2c calls as no-ops). The shim directory is
  first on the include path, so the real `headers/` files still supply
  everything else.
- `config.pb.h` / `enums.pb.h` are the real nanopb-generated headers, reused
  from `build/proto` (regenerated by `build.sh` if missing).

If the firmware display code starts using a new `Storage`/`System` method, the
simulator fails to **compile** rather than drifting silently.
